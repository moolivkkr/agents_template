## 2. Refuted or overstated

**SRE-01: CRITICAL → HIGH.** Every citation checks out. `/rollback` for local, staging and prod reverses migrations before redeploying, and it names `prisma migrate reset` as an example. That command drops the database. Three things lower the severity:

- The prod path requires `--confirm`, and the prompt at `rollback.md:52-56` tells the human it will "Reverse migrations applied in the last deploy".
- Step 2's trigger file, `agent_state/deploy/last-migrations.json`, is written by nothing in the repo, and neither is Step 1's `previous-sha.txt`. The step is effectively driven by the LLM's own inference.
- Since Prisma ORM 6.15 (Aug 2025), `migrate reset --force` detects Claude Code and refuses without an explicit consent env var.

The data loss is also narrower than claimed: DOWN migrations drop only the objects the release added. It is still HIGH, because staging auto-proceeds and the ordering is wrong. The redeploy should come first, since old code tolerates extra columns. Two quick wins, independent of the rest of the backlog: remove `prisma migrate reset` and `flyway undo`, and put the redeploy before any DOWN migration.

**SRE-02: PARTIAL, → MEDIUM.** The central incident, a rename with no dual-write reaching prod, is already blocked. `migration_safety_reviewer` Check 1 (`:74`) flags a RENAME HIGH. Check 5 (`:123-131`) requires expand-then-contract and marks a rolling-deploy incompatibility HIGH (BLOCKING). The orchestrator adds that reviewer to the roster whenever migrations exist. The parts that remain true:

- the author template labels a plain `CREATE INDEX` "safe";
- the reviewer rates it only MEDIUM, so it doesn't block;
- `deploy.sh` applies the manifests, which starts the rollout, before the migrate Job runs. If migrate then fails, new code stays live on the old schema in dev/qa.

The migration_safety_reviewer severity for a non-concurrent index on an existing table should go up, and the deploy.sh order should be fixed. Both are MEDIUM-grade.

**SRE-03: PARTIAL, stays HIGH.** Two statements are wrong: "No agent implements idempotency keys on POST", and the "Missing entirely" bullet on idempotency keys. `api_developer.tmpl:47` loads `api-excellence.md`, which mandates `Idempotency-Key` on every POST and includes a middleware implementation (`:346-418`, `:544`). The outbound half is correct: the shared `Retry` wrapper retries timeouts and any 5xx whatever the method, with no retry budget, and no integration test sends a duplicate POST. That is where the double-charge incident comes from, so HIGH stands.

**SRE-06: HIGH → MEDIUM.** The skill and the manifests do lack a preStop delay and a grace-period budget. The consequence is a transient burst of errors per rollout, with no data loss. In the only Kubernetes target the framework runs (the dev/qa lab), smoke tests run after rollout, so no gate is affected. The reviewer's "GA in Kubernetes 1.32 (verified)" is wrong. KEP-3960 graduated to stable in 1.34; it has been beta and on by default since 1.30, so the recommendation still works.

**SRE-10: PARTIAL, → MEDIUM.** "No tier proves that a timeout fires" is too strong. `integration_test_agent` loads `external-service-mocks.md`, which requires testing "timeouts, 4xx, 5xx responses (ensures graceful degradation)" for external services. The template line about a DB being unreachable concerns a broken test environment, not a decision that outages can't be tested. What is genuinely absent is a failure-injection case class for infrastructure dependencies (DB or cache down, breaker opening, readiness flip, SIGTERM, pod kill). That is a real maturity gap but not a likely normal-run defect.

**OPS-01: CRITICAL → HIGH.** The core claim holds: no /develop wave packages or deploys the app, and the 22 agents contain none of the runtime-contract terms. Two parts are overstated:

- backend_developer is taught `/healthz` and `/readyz` by `resiliency-patterns.md`.
- The k8s layer exists only after `deployment_agent` has created it, and its instructions (`:218-240`) are to point `jobs.yaml` at the app's real migrate/seed commands, adapt `images.txt` and the probes, then run `deploy.sh dev`. The "unknown command `migrate`" chain is therefore not deterministic.

Scenario (2) is real: no compose file means Wave 3.5 only runs `go build`, and acceptance has nothing to test. It fails loudly (acceptance reports BLOCKED) rather than passing silently. HIGH, the same as the duplicates ARCH-10 and DEV-10.

**OPS-02: CRITICAL → HIGH.** All the evidence is correct, and ARCH-09 adds a stronger point: orchestrator bash blocks run in fresh shells (`:783`), so the `APP_BASE_URL` export never reaches anything. Two things lower the severity:

- Web E2E exercises the same commit through the dev server, so functional coverage exists; what is missing is artifact identity.
- On a k8s project, acceptance fails loudly at the Track B `localhost/health` prerequisite.

HIGH, consistent with ARCH-09 and TEST-09.

**OPS-04: HIGH → MEDIUM.** Confirmed, and worse than stated. `agent_state/` is not gitignored, so a repo-root build context is always `-dirty` during /develop. The effect is on provenance in disposable environments. Rollback redeploys by digest and is unaffected, and pruning keeps HEALTHY digests whether dirty or not.

**OPS-05: HIGH → MEDIUM.** I reproduced all four behaviours: Go returns `(cached)` with no test counts, Jest rejects `--run`, and pytest rejects `--integration`. The Go separation mechanism, however, exists: `testcontainers.md:130` (`//go:build integration`) is loaded by `integration_test_agent` and matches test_runner's `-tags=integration`. test_runner's own `targeted-testing.md:97` also tells it to use `-count=1`.
