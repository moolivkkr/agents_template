## Refuted or overstated

**TEST-01 (PARTIAL, stays CRITICAL).** The headline reproduction ("verify-gate passed 10 failing unit tests") only works with a roster that drops `test_runner`. In the normal base roster (orch:187), test_runner's `test_results.json` carries `total` and `failed`, and verify-gate blocks on `failed>0`. My scenario C reproduced that (`reports failed=10`, exit 2). The core claim still holds and is CRITICAL:
- The e2e, acceptance and web UI reports have no sidecar and no count line. verify-gate's fallback checks only `total: 0`, `SKIPPED` and the word BLOCKING.
- In scenario B, a FAIL e2e row plus a FAIL acceptance report with a CONTRACT_VIOLATION BLOCKER passed under the full base roster.
- Worse than the reviewer reported: in scenario D, an acceptance report that says "BLOCKED — deployment not healthy" with every use case UNTESTED also passed. The awk matches BLOCKING, not BLOCKED.

**TEST-02 (CONFIRMED, CRITICAL → HIGH).** Every mechanism reproduces: recycled phase-1 IDs, `t.Skip` tests, TODO comments and range endpoints all count as covered. Nothing enforces cross-phase uniqueness beyond an anti-pattern table row. I rate it HIGH rather than CRITICAL for three reasons:
- The failure is missing tests passing the gate, not failing behaviour passing it.
- The same agent's Direction A behaviour-level check (spec_test_reconciler.md:122-133) is a backstop, though LLM-judged.
- The bash/BSD-grep fail-open that the reviewer also reproduced (I reproduced it too) is macOS-and-bash specific. On this machine, agents' Bash tool runs zsh with a Claude Code grep wrapper backed by ugrep, which supports `-P`. Linux GNU grep supports `-P` as well. The reconciler's DoD (:273) also says "A PASS with zero spec behaviors and zero TC-* IDs compared is a FAIL to investigate".

The `grep -c … || echo 0` → `"0\n0"` bug reproduces in both shells, which bears on TEST-17.

**TEST-03 (PARTIAL, CRITICAL → HIGH).** Correct:
- test_runner runs once.
- Wave 4 fixes are "verified" by re-running the reviewer only.
- The app is redeployed only for CONFIG failures.
- Check (e) is never switched on, because nothing creates `sdlc-verify.json`.

Wrong: "nothing re-runs the suites before gate.passed".

The genuine gap is that these re-runs are LLM-executed, not bound to HEAD, and use `tee` (TEST-05), while e2e and acceptance evidence predates the fixes and the redeploy. That is serious (HIGH) but not an automatic pass.

**TEST-07 (PARTIAL, HIGH → MEDIUM).** The claim "the contract oracle is the implementer's description, so contract checks cannot fail" ignores three counter-points:

- spec_impl_reconciler compares code to spec.

The integration tier alone is self-referential, and the OpenAPI "matches" gate is trivial when the spec is generated from code (a real but secondary issue, DEV-18). The unit-tests-from-source and implementer-written-tests points hold.

**TEST-10 (CONFIRMED, HIGH → MEDIUM).** Every cited line is accurate, and `failOnFlakyTests` does exist (Playwright ≥ 1.52). But retrying e2e and reporting pass-on-retry is common industry practice. The failure scenario, a product race classified as FLAKY and patched in the test, is plausible but not the expected outcome of a normal run, and no framework control claims to prevent it. The useful fix, a FLAKY state for web e2e plus `-race`/repeat runs for changed tests, is a hardening item.
