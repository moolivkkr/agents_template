# React Native (iOS + Android) — platform facts testing agents need

Not a full RN development guide. This is what the test writers, E2E runners and platform auditor must
know to test an RN app correctly. Testing strategy: `../testing/mobile-testing-strategy.md`.

> **Verified 2026-09-29, re-check per project.**
> - RN **0.87** (2026-08-11) is current; 0.88 is in RC.
> - The New Architecture (Fabric + TurboModules) is the **only** architecture since 0.82; TurboModules are always on in 0.87.
> - Hermes V1 has been the default engine since 0.84.
> - RN 0.87 requires Node ≥ 22.13 and makes the Strict TypeScript API the default, so deep `react-native/Libraries/*` imports are type errors.
> - Minimums for RN 0.87: **iOS 15.1**, **Android minSdk 24** (targetSdk 36).
> - Expo SDK 57 (RN 0.86, React 19.2) is stable; SDK 58 is in beta.
> - The RN docs recommend starting new apps with a framework (Expo).
> Take the project's actual versions from `package.json` and `docs/IMPLEMENTATION_GUIDELINES.md`,
> not from this note.

## Project shapes

| Shape | Native folders | Build for device tests | Notes |
|---|---|---|---|
| Expo managed / CNG | generated by `expo prebuild` (usually git-ignored) | EAS Build profiles, or `npx expo run:<platform>` | Config plugins own native config. Never hand-edit generated `ios/`/`android/` |
| Bare RN | `ios/` + `android/` checked in | `xcodebuild` / `gradlew` | Native changes are code-reviewed like any source |

## What differs between platforms (test both)

- **Networking to the local backend:** iOS simulator → `localhost`. Android emulator → `10.0.2.2`.
  Android blocks cleartext HTTP by default, so the E2E/debug build needs a
  `network_security_config` allowing `10.0.2.2`. Release builds must NOT allow cleartext to real
  hosts; `mobile_platform_auditor` checks this.
- **Secure storage:** tokens belong in Keychain/Keystore (`expo-secure-store`,
  `react-native-keychain`), never AsyncStorage.
- **Permissions:** iOS needs a usage-description string in `Info.plist` for every permission, or the
  app crashes (and App Store review rejects it). Android needs `<uses-permission>` in the manifest
  plus a runtime request for dangerous permissions.
- **Deep links:** iOS Universal Links need `apple-app-site-association` plus the associated-domains
  entitlement. Android App Links need `assetlinks.json` plus `autoVerify` intent filters. Custom
  schemes work on both but are not verified.
- **Back:** Android has system back (`BackHandler`); iOS has none except the navigation swipe gesture.
- **Text:** iOS Dynamic Type and Android font scale both scale `Text` unless `allowFontScaling={false}`,
  which is an accessibility defect unless justified.

## Accessibility props (RN ≥ 0.71)

RN supports web-style `role` and `aria-*` props (`aria-label`, `aria-hidden`, `aria-checked`,
`aria-disabled`, `aria-expanded`, `aria-selected`). They take precedence over the older `accessibilityRole` /
`accessibility*` props, which are still supported (not deprecated). Either style satisfies the
accessibility check; mixing both on one element is a review WARNING because the precedence is easy
to misread.

Minimum touch target: 44×44 pt (Apple HIG) / 48×48 dp (Material). `hitSlop` counts toward the target.

## Build variants the pipeline uses

| Purpose | Variant |
|---|---|
| Component/integration tests | none (Jest in Node) |
| Device E2E + acceptance | **Release** build pointing at the local backend (E2E env config) |
| Store submission | Release build with production config (not tested by the pipeline) |

## Health check for Wave 3.5 (mobile)

"Healthy" for a mobile app means all of:
1. Both binaries built (`.app` for the iOS simulator, `.apk` for the Android emulator).
2. Each installs on its booted device.
3. Each cold-launches to its first screen within the startup budget with no native crash and no
   red screen.
4. The first screen's network call reaches the Wave 3.5 backend (seen in backend logs or on screen).
